## 2. Core Architecture & Strict Invariants

1. **Single-File Architecture (`index.html`):**
   - The primary application logic, responsive styles, and layout reside in `index.html` (single-file distribution).
   - Do not introduce heavy frontend frameworks (React, Vue), build bundlers (Webpack, Vite), or external package dependencies unless explicitly instructed by the repository owner.
   - Auxiliary files must be maintained in sync:
     - `manifest.json`: Web app manifest (PWA metadata, icons, theme color).
     - `sw.js`: Service worker caching logic.
     - `supabase/schema.sql`: Database tables, indexes, and Row Level Security policies.
     - `README.md`: Setup guide and operational instructions.

2. **Full Localization Coverage (`I` Dictionary):**
   - The application strictly supports bilingual interface: Ukrainian (`uk`) and English (`en`).
   - Every user-facing string (labels, placeholders, buttons, notifications, modal titles, error messages) MUST be routed through the `I` translation object.
   - Never hardcode strings in UI templates or scripts without corresponding `uk` and `en` entries.
   - Keep 100% dictionary key parity between `I.uk` and `I.en`.

3. **Data Loss Prevention & Storage Resilience:**
   - User profile, goals, daily food entries, and weight logs are stored in `localStorage` under key `smartdiet-v1`.
   - Any schema or data structure update MUST preserve backwards compatibility with existing stored user data. Never wipe, rename, or reset `smartdiet-v1` without a safe migration fallback.
   - Local state must seamlessly merge or synchronize with Supabase when cloud sync is configured.
   - **Never expose Supabase `service_role` key in client-side code.** Only public `anon` key with properly configured Row Level Security (RLS) is allowed in the browser.

4. **AI Providers & Model Integration:**
   - The app supports Google Gemini and OpenAI as AI providers for meal portion and nutrition estimation.
   - API endpoints and model identifiers must match official provider specifications:
     - For Google Gemini: use actively supported stable models (e.g., `gemini-2.0-flash` or newer documented endpoints); do not use discontinued models.
     - For OpenAI: use current lightweight models (e.g., `gpt-4o-mini`).
   - API keys are stored solely on the client device in `localStorage`; never transmit user API keys to third-party proxy servers without explicit consent.
   - Always surface raw provider error messages in a user-friendly way so the user can easily diagnose missing keys, rate limits, or invalid model errors.

5. **Dietary & Safety Guardrails:**
   - Calculations and AI estimations are approximate nutritional estimates and NOT medical advice.
   - Maintain visible safety notices and disclaimers across the UI and in AI system prompts (e.g., adult guidance 18+, consulting healthcare professionals, warnings against aggressive calorie restriction).
   - Calorie calculations must enforce reasonable minimum thresholds to prevent unsafe dietary recommendations.

6. **Responsive Layout & Mobile Adaptation:**
   - The application is designed mobile-first as an installable PWA.
   - Mobile navigation bar (`.mobilebar`), sticky headers, chat panels, modals, and input keyboards (`inputmode="numeric"`, `inputmode="decimal"`) must work flawlessly on narrow viewports (360px - 430px) and iOS Safari with notch/home indicator safe areas (`env(safe-area-inset-*)`).
   - Modals must be cleanly dismissible via close buttons (✕), backdrop clicks, or cancel actions.
