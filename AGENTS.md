## 1. Core Operating Principles

0. **Never Edit This Instruction Without Asking First:**
   - AI agents must never modify, expand, restructure, or delete anything in this file on their own initiative — not even a fix to an obvious typo or contradiction.
   - If an agent identifies something that should be added, removed, or changed here, it must first explicitly describe the proposed change to the repository owner and wait for approval. Only after explicit approval may it edit this file.

1. **Two Execution Modes — Direct Instructions vs. Critique/Feedback:**
   - **Direct instruction** ("fix X", "add Y", "change Z", "remove W"): execute directly without pausing to ask "should I do this?" or "are you sure?". Complete the work, then report what was done concisely. Silence about a step is not permission to skip it — if something in the instruction is genuinely ambiguous, pick the most reasonable, safe interpretation, state the assumption in your reply, and proceed.
   - **Critique or open-ended feedback** (the user points out something looks off, asks what you think, or raises a concern without a concrete task attached): analyze first — explain implications, edge cases, and alternatives — and wait for the user's explicit go-ahead before touching code.
   - A direct instruction that turns out to be risky (schema change, altered storage keys, breaking UI flows, API signatures) is still executed — flag the risk clearly in your reply as you make the change.

2. **Zero AI Footprint (Strict Clean Code Invariant — MANDATORY):**
   - Strictly forbidden to leave any trace of AI generation in the repository.
   - Never include AI-related comments, headers, docstrings, notices, watermarks, or commit trailers (e.g., no "Generated by Claude", "AI-assisted", "Co-authored-by: AI", ChatGPT/Claude/Copilot disclaimers).
   - Actively remove any pre-existing AI markers or boilerplate artifacts when modifying files.
   - All code, comments, documentation, and commit messages must look strictly human-written and maintain a clean, professional engineering standard.

3. **Strict GitHub Profile Identity & Publications (MANDATORY):**

     - Name: `Denys`
     - Username: `kdinya`

   - Never commit, push, or publish under any AI tool identity, bot account, cloud assistant address (e.g. `assistant@lovable.dev`, `ai@example.com`), or generic machine placeholder.
   - Check `git config user.name` and `git config user.email` before any local commit to ensure it matches the repository owner.

4. **Source of Truth: Always Read the Actual Latest Repository State:**
   - Before performing any repository task, check the repository for open pull requests. Review their titles, base and head branches, draft status, and changed files to identify work that is related to or could conflict with the task. Continue relevant work on its existing branch or coordinate around the conflict; do not duplicate, overwrite, or discard in-progress changes.
   - Before performing any task, read current files / latest commit on `main` directly. Never rely on chat history, memory, or a previously discussed code state.
   - Check `git fetch` and ensure `origin/main` has not moved unexpectedly before pushing.
   - Maintain minimal diffs: modify only the lines and files directly pertinent to the task. Avoid unprompted mass reformatting.

5. **User Communication & Tone:**
   - Communicate with the repository owner in Ukrainian.
   - Keep responses concise, direct, and focused on technical execution without boilerplate filler or unnecessary pleasantries.
   - Follow conventional commits (`feat:`, `fix:`, `docs:`, `perf:`, `refactor:`, `test:`, `chore:`).
6. **Styled Interface Only (MANDATORY):**
   - Every popup, confirmation, notice, and picker must use the application's own styled components: `.modal-back` dialogs, the wheel picker, the in-app calendar, and the styled confirmation dialog (`askConfirm`).
   - Native browser dialogs (`window.confirm`, `window.alert`, `window.prompt`) and native date or time picker popups are forbidden.
   - The browser's own install prompt (`beforeinstallprompt`) is the only exception, because the browser controls it.
7. **Report Defects Found During Any Edit:**
   - If an agent notices a bug, risk, or inconsistency in the application while working on any edit, it must report it to the repository owner in its reply, even when the issue is outside the current task.
8. **Language of This File & Documentation:**
   - This instruction file must be written in English.
   - All repository documentation must be provided in two languages: English (`README.md`) and Ukrainian (`README.uk.md`). Both versions must describe the same features and be kept in sync.
9. **Direct Repository Work:** For all application changes, work directly in the GitHub repository `kdinya/smart-diet-ai`; do not ask the user to create or open a Lovable project.
10. **Application Versioning:** Use `YYYY.MM.N` for every application release. Use the release year and month, with a sequence number starting at `1` for the first release in that month; increment the sequence for each additional release in the same month, and reset it to `1` when the year or month changes. Display the current app version in Settings and keep it synchronized with the release tag. When preparing release notes, always list changes in this order: **Added**, **Fixed**, then **Improved**; omit a category when there are no changes in it. When a change is small or non-critical (a label, wording, icon, or minor layout tweak), describe it generally in one short line, such as "Improved minor interface details", instead of listing the specific fields, labels, or wording that changed. Name a specific item only when it is a new feature or matters to users. Create a new application version, tag, or GitHub Release only when the user explicitly asks for a new version/release. For ordinary feature, fix, or improvement work without that explicit request, keep the current version and tags unchanged and update the latest version entry in the in-app version history by adding a concise description of the new functionality or improvements, preserving the required release-note category order.

11. **Safely Save In-Progress GitHub Work:** For significant, multi-step, or unfinished changes, work in a dedicated branch created from the latest `main`. Save meaningful intermediate checkpoints as commits and push them to that branch so the work can be resumed later. Open a draft pull request when review or automated checks are useful; a draft PR is for review, while the branch commits are the saved work. Merge into `main` as soon as the change is complete and all relevant required checks pass; do not ask the repository owner for a separate merge approval. If any required check fails or an issue remains, do not merge. After merging, delete the feature branch when it is no longer needed. Do not create a branch or PR for a small, isolated change unless the repository owner requests it.

   - Never break schema compatibility for `state.diary`, `state.products`, `state.weights`, `state.profile`, or `state.foods`.
   - Always preserve user state during updates, migrations, and error fallbacks.

3. **Task-Based File Routing (Read & Edit Only What You Need):**
   - **Translations / wording:** `js/i18n.js` only. Keep `I.uk` and `I.en` keys 100% synchronized.

   - **Local Domain Tasks** (changes strictly inside `js/calc-nutrition.js`, `js/ai-service.js`, `js/storage.js`, `js/i18n.js`):
     - Do not touch `index.html` or `css/*`.
     - Verify with `npm run check` and relevant unit tests (`npm run test:unit:<target>` or `npm run test:unit`).
     - Do not run the full Playwright smoke suite for pure domain logic.

## 3. Pre-Flight Verification Checklist

### Test Requirements
- Before changing code, inspect `package.json` and the relevant CI workflow to identify the available test commands and checks.
- Start with the narrowest relevant test(s) for fast feedback. After a fix, rerun the failed test and directly related checks before repeating unrelated suites. For UI behavior, use the matching Playwright smoke tests; run the full smoke suite as a final gate when changes affect shared flows or when practical.
- Targeted tests are an early feedback loop, not a replacement for required CI checks. Before merging, confirm that all required PR checks pass.
- Run the applicable syntax/static checks from CI for the files changed. Do not claim a test passed unless it was actually run and its result was observed.
- Do not weaken, remove, or broadly skip a test just to make a run green. Fix stale assertions only when they conflict with the intended behavior, and add regression coverage for the behavior being changed.
- In the completion report, name the commands run and summarize pass/fail counts. Clearly state any suite that could not be completed and why.
- **Efficient, High-Quality Edits:** Strictly follow the Task-Based File Routing rules (Section 2.2). Read only the code sections a change needs (targeted searches and line ranges, not full reads of `index.html`). Batch related edits into one branch and one PR, and iterate with the narrowest failing test before running the full smoke suite once as the final gate. Run the database job only when database, schema, auth, or sync code changes. Every UI change adds or updates a regression test, including a 360px layout check where inputs or controls change.

3. **End-to-End Flow Verification:**
   - Verify onboarding modal logic (first launch, language choice, dismissibility, and saving).
